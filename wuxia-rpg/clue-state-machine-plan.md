# 线索状态机改造方案

> 状态：设计稿，尚未实施。适用于当前 AI 驱动叙事与 `go → judge` 引擎流程。

## 一、目标

将现有“名称 + 进展节点 + 关闭”的线索日志升级为：

```text
任务契约（GM隐藏）
+ 任务事实（引擎持久化）
+ 自动状态归约（引擎执行）
+ 进展节点（玩家可见）
```

核心原则：

1. LLM 提交“发生了什么”，不手动维护当前阶段。
2. 引擎由结构化事实自动推导阶段和终局。
3. 状态机管理任务生命周期，不作为玩家行动的硬门锁。
4. 只处理本轮相关任务，不向 LLM 注入全部未完结任务。
5. 路径可动态扩展，但既有事实、不变量和历史不可被随意改写。

## 二、现状与问题

当前线索存于 `explore.json.任务摘要及进度`：

```json
{
  "名称": "某条线索",
  "进展节点": [{"描述": "……", "奖励": "经验800"}],
  "关闭": false
}
```

现有机制的问题：

- 引擎只按名称整体替换，不理解任务阶段、事实和终局类型。
- LLM 依赖自然语言节点回忆任务状态，容易遗漏或改写前因后果。
- `关闭` 不能区分解决、失败和失效。
- 每次重传完整节点，存在丢历史、重复奖励和覆盖隐藏数据的风险。
- 完整线索主要在读档或自动存档时回传，日常推演缺少稳定的按需查询。

## 三、目标数据模型

```json
{
  "标识": "taihu_bandit_crisis",
  "名称": "太湖水寨之患",
  "作用域": {"类型": "地区", "区域": ["苏州"]},
  "关联": {
    "人物": ["薛四彭", "耿朱桥", "石敬岩"],
    "地点": ["太湖", "苏州码头", "水寨"],
    "物品": ["水寨兵册"],
    "事件": ["角色死亡", "兵力集结", "官府出兵"],
    "世界事实": ["suzhou_under_attack"]
  },
  "状态机": {
    "不变量": ["薛四彭正在扩充水寨兵力"],
    "阶段": [
      {"标识": "hook", "名称": "异状浮现"},
      {"标识": "investigating", "名称": "追查中"},
      {"标识": "crisis", "名称": "冲突激化"},
      {"标识": "resolved", "名称": "事态解决", "终局": "解决"},
      {"标识": "failed", "名称": "事态失控", "终局": "失败"},
      {"标识": "expired", "名称": "线索失效", "终局": "失效"}
    ],
    "转移": [
      {
        "来源": "hook",
        "目标": "investigating",
        "条件": {"事实": "water_fort_discovered", "等于": true}
      },
      {
        "来源": "investigating",
        "目标": "crisis",
        "条件": {"事实": "suzhou_attack_started", "等于": true}
      }
    ],
    "全局终局": [
      {
        "目标": "resolved",
        "条件": {"事实": "xue_sipeng_neutralized", "等于": true}
      }
    ]
  },
  "当前阶段": "hook",
  "事实": {
    "water_fort_discovered": false,
    "suzhou_attack_started": false,
    "xue_sipeng_neutralized": false
  },
  "调度": {
    "层级": "休眠",
    "最后相关轮次": 0,
    "下次时间触发": null
  },
  "进展节点": [
    {"描述": "酒客谈及太湖近来常有兵刃船只出没。"}
  ]
}
```

### 字段职责

| 字段 | 可见性 | 职责 |
|---|---|---|
| `标识` | GM | 稳定主键，创建后不可修改 |
| `名称` | 玩家 | 线索栏名称 |
| `作用域/关联` | GM | 候选任务路由与唤醒 |
| `状态机` | GM | 阶段、转移、不变量、终局条件 |
| `事实` | GM | 任务局部权威状态 |
| `当前阶段` | GM | 引擎归约结果，不由 LLM 直接维护 |
| `调度` | GM | 前台、活跃、休眠、终局及时间触发 |
| `进展节点` | 玩家 | 已获知的客观进展与奖励 |

阶段状态由引擎推导：

```text
非终局阶段 → 进行中
终局=解决 → 已解决
终局=失败 → 已失败
终局=失效 → 已失效
```

## 四、任务创建与推进

### 1. 创建

只有可持续推进的委托、冲突或悬案创建状态机；一次性情报并入已有线索节点。

创建时由 LLM 提交：

```json
{
  "类型": "线索",
  "操作": "创建",
  "标识": "taihu_bandit_crisis",
  "名称": "太湖水寨之患",
  "作用域": {},
  "关联": {},
  "状态机": {},
  "初始事实": {},
  "初始阶段": "hook",
  "新增节点": [{"描述": "……"}]
}
```

引擎验证阶段、转移、条件引用和标识唯一性后落盘。

### 2. 推进

LLM 只提交任务事实或通用剧情事件：

```json
{
  "类型": "线索事实",
  "标识": "taihu_bandit_crisis",
  "设置": {"water_fort_discovered": true},
  "新增节点": [{"描述": "玩家问出了水寨方位。", "奖励": "经验1000"}]
}
```

或：

```json
{
  "类型": "剧情事件",
  "事件": "供认",
  "主体": "师爷",
  "地点": "县衙",
  "内容": "承认毒杀县令"
}
```

引擎根据订阅关系将通用事件映射到相关任务事实。

### 3. 状态归约

每轮事实变化后，引擎执行：

```text
应用机械状态变化
→ 生成领域事件
→ 路由到候选任务
→ 应用剧情事件/任务事实
→ 连续检查当前阶段转移
→ 检查全局终局
→ 直到无可用转移
→ 原子提交
```

允许一次归约跨过多个已满足阶段，修复前序阶段滞后。全局终局可从任意非终局阶段触发。

### 4. 动态扩展

玩家提出合理但未预设的方案时，允许追加阶段、转移、关联或事实定义；禁止删除历史阶段、修改不变量或覆盖既有事实。

## 五、任务路由与上下文控制

### 1. 反向索引

引擎按以下维度建立任务索引：

```text
人物 → 任务ID集合
地点 → 任务ID集合
物品 → 任务ID集合
事件类型 → 任务ID集合
世界事实 → 任务ID集合
地区 → 任务ID集合
```

本轮候选集为相关索引的并集，不扫描并注入全部任务。

### 2. 时间队列

有期限或后台发展的任务登记 `下次时间触发`，按时间排序；时间跨过触发点时才唤醒，不要求 LLM 每轮检查。

### 3. 活跃层级

```text
前台：当前数轮正在推进，通常1～3条
活跃：近期可能触发，引擎监控但默认不注入
休眠：远程或暂无触发条件
终局：只保留历史结果和世界影响
```

“未完结”不等于“每轮活跃”。

### 4. LLM 上下文预算

普通回合只返回：

```text
当前场景
+ 本轮事件
+ 0～3条相关任务的当前转移前沿
```

紧凑任务卡示例：

```json
{
  "标识": "magistrate_murder",
  "名称": "县令之死",
  "当前阶段": "confrontation",
  "命中原因": ["人物：师爷", "事件：供认"],
  "相关事实": {
    "secretary_confessed": false,
    "truth_public": false
  },
  "待裁定": ["本轮言辞是否构成有效供认"]
}
```

完整状态机仅在扩展、异常或主动查询时返回。

## 六、遗漏与一致性保护

确定性引擎无法可靠从叙事文本判断 LLM 是否漏提交剧情事实，因此采用多层保护：

1. 机械变化自动生成领域事件，如死亡、得物、抵达、战斗结束。
2. Skill 强制要求持续性剧情后果以 `剧情事件` 或 `线索事实` 落盘。
3. go 根据人物、地点、物品和事件返回“可能受影响线索”提醒。
4. 阶段由事实自动归约，不要求 LLM 手动提交目标阶段。
5. 阶段滞后时允许连续校准，不因旧阶段阻断合法玩家行动。
6. 自动存档时由引擎全量检查，只向 LLM 返回异常摘要。

状态机不得作为玩家行动的绝对门锁；行动是否合法仍由人物、地点、物品、判定和世界状态决定。

## 七、条件 DSL

首版仅支持任务局部事实：

```text
等于、不等于、大于、大于等于、小于、小于等于、包含
全部、任一、非
```

示例：

```json
{
  "全部": [
    {"事实": "culprit_identified", "等于": true},
    {"事实": "evidence_strength", "大于等于": 3}
  ]
}
```

后续再接入角色死亡、物品持有、位置、关系度和时间等权威世界状态，避免首版扩大为全局规则引擎重构。

## 八、玩家视图与 GM 视图

玩家 `查看线索` 只显示：

- 名称；
- 已获进展节点；
- 节点奖励；
- 已解决、已失败或已失效。

不得返回状态机、不变量、隐藏事实、未满足条件和预设结局。

GM 接口分为：

```text
摘要：标识、名称、当前阶段、状态、命中原因
前沿：当前相关事实和可触发变化
完整：状态机、不变量、全部事实和历史节点
异常：需要校准或人工裁定的问题
```

## 十、旧存档兼容

第一版保留 `explore.json.任务摘要及进度` 字段名，只升级内部结构。

旧线索惰性迁移：

```text
关闭=false → 遗留进行中
关闭=true → 遗留已结束
无状态机 → 遗留线索，首次再次涉及时由 LLM 建模
```

迁移时保留全部名称、节点和奖励，不由引擎凭空生成旧任务真相。新数据按稳定 `标识` 合并；无标识旧数据暂按名称兼容。

## 十一、测试要求

至少覆盖：

- 状态机结构、阶段和条件引用校验；
- 合法转移、非法转移、连续归约、全局终局；
- 机械事件与剧情事件路由；
- 任务事实、节点和其他 judge 变化的原子回滚；
- 动态扩展只能新增；
- 终局后禁止普通推进；
- 玩家视图不泄露隐藏数据；
- 查询只返回所需粒度；
- 自动存档、读档和旧线索迁移；
- 多任务索引、地区过滤和时间触发。

## 十二、实施顺序

### 阶段一：模型与存档

- `clue_store`、稳定标识、事实、阶段图、公开/隐藏投影；
- 创建、事实更新、自动连续归约；
- 旧档兼容和单元测试。

### 阶段二：事件路由与上下文

- 机械领域事件、通用剧情事件；
- 人物/地点/物品/事件/地区反向索引；
- `wuxia_clue_query`、当前转移前沿和上下文预算。

### 阶段三：调度与世界联动

- 时间队列、前台/活跃/休眠管理；
- 世界事实依赖与跨任务唤醒；
- 自动存档一致性扫描和异常摘要。

## 十三、非目标

首版不做：

- 每轮把全部任务交给 LLM；
- 从自然语言剧情自动猜测权威事实；
- 让任务阶段阻止合法世界行为；
- 一次性把所有预设故事线编译成状态机；
- 首版接入完整全局世界条件 DSL；
- 修改战斗系统或 `assets/data/`。
